## Overview

The `ajs project modules` command group edits the modules of `antelope.config.ts` and downloads them. Every command of the group accepts the global options and the `-p, --project` and `-e, --env` options that [Project commands](/docs/cli/project#overview) describes.

The commands that write `antelope.config.ts` edit only the values they change, in place. Imports, constants, `process.env` reads, calls such as `resolve(__dirname, ...)`, comments and formatting stay as you wrote them. A command changes a value only when the file holds it as a plain literal, such as a string, a number or an object of literals. When the value is an expression, such as `version: CORE_VERSION`, the command fails, names the value and the edit to make by hand, and leaves the file unchanged. `ajs project logging set` writes the file the same way.

## Module management

These subcommands add, remove, list and update the modules of a project, and add the modules that its unresolved interfaces need.

### `ajs project modules add`

Add one or more modules to the project configuration and download them.

```bash
ajs project modules add <modules...> [options]
```

| Argument  | Description                                                  |
| --------- | ------------------------------------------------------------ |
| `modules` | npm packages, repository URLs or paths, depending on `--mode` |

| Option                    | Description                                                         |
| ------------------------- | ------------------------------------------------------------------- |
| `-m, --mode <mode>`       | Source of the modules: `package`, `git`, `local` or `dir` (default: `package`) |
| `-p, --project <path>`    | Path of the project folder (default: current directory)             |
| `-e, --env <environment>` | Environment of `antelope.config.ts` to add the modules to           |

| Mode      | Argument                                                     | Listed as |
| --------- | ------------------------------------------------------------ | --------- |
| `package` | An npm package name, optionally with a version, range or dist-tag | `npm`     |
| `git`     | A repository URL                                             | `git`     |
| `local`   | The folder of one module, with a `package.json`              | `local`   |
| `dir`     | A folder whose every subfolder is a module                   | `folder`  |

The last column is the source that `ajs project modules list` shows for the module.

In `package` mode, give a module as `<name>` or `<name>@<spec>`. The spec is an exact version, a semver range or a dist-tag. Without a spec, the command writes the latest published version as a caret range (`^1.3.2`), so the module follows new minor and patch releases. To pin the module, pass an exact version. The command rejects an invalid spec at once, and it does not add a module whose download fails.

In `local` mode, the module is added under the `name` of its `package.json`. When that `package.json` has no name, the folder name is used instead.

**Examples:**

```bash
# Add the latest version of an npm package (writes a ^ range)
ajs project modules add @antelopejs/api

# Pin an exact version
ajs project modules add @antelopejs/api@1.3.2

# Use a semver range or a dist-tag
ajs project modules add @antelopejs/api@~1.3.0
ajs project modules add @antelopejs/api@next

# Add a module from a local folder
ajs project modules add ./modules/auth --mode local

# Add several npm modules at once
ajs project modules add @antelopejs/api @antelopejs/mongodb
```

```text
✔ Added @antelopejs/api 1.3.2 5.0s
1 module added to antelope.config.ts · 5.2s

Next steps
  ajs project modules install  resolve the interfaces they need
```

### `ajs project modules remove`

Remove one or more modules from the project. The alias is `rm`.

```bash
ajs project modules remove <modules...> [options]
ajs project modules rm <modules...> [options]
```

| Argument  | Description                        |
| --------- | ---------------------------------- |
| `modules` | Names of the modules to remove     |

| Option                    | Description                                               |
| ------------------------- | --------------------------------------------------------- |
| `-p, --project <path>`    | Path of the project folder (default: current directory)   |
| `-e, --env <environment>` | Environment of `antelope.config.ts` to remove them from   |
| `-f, --force`             | Remove the modules found even if some names are unknown   |

Without `--force`, the command removes nothing when one of the names is not in the configuration.

**Example:**

```bash
ajs project modules remove @antelopejs/api --force
```

### `ajs project modules list`

List the modules of the project. The alias is `ls`.

```bash
ajs project modules list [options]
ajs project modules ls [options]
```

| Option                    | Description                                             |
| ------------------------- | ------------------------------------------------------- |
| `-p, --project <path>`    | Path of the project folder (default: current directory) |
| `-e, --env <environment>` | Environment of `antelope.config.ts` to list             |
| `-j, --json`              | Print the result as JSON on stdout                      |

The command prints a table of the modules with their name, source (`npm`, `git`, `local` or `folder`) and reference (version, repository or path). On a narrow terminal, an ellipsis cuts long references. On a terminal too narrow even for that, each module is a block of `NAME`, `SOURCE` and `REFERENCE` lines. When stdout is piped, each module is one tab-separated line without a header. With `--json`, the command prints an array of `{ "name", "source" }` objects, where `source` is the module source as configured.

**Examples:**

```bash
ajs project modules list

# Print the module names only
ajs project modules list | cut -f1
```

```text
ℹ 3 modules in acme-shop (default)
NAME                  SOURCE  REFERENCE
@antelopejs/api       npm     1.0.0
@antelopejs/auth-jwt  npm     ^1.0.0
billing               local   modules/billing
```

### `ajs project modules update`

Check npm for newer versions of the npm modules of the project and write them to the project configuration. Without arguments, the command updates every npm module. To update only some modules, pass their names. The command leaves modules from git or local folders as they are.

The command also resolves the dependencies of each updated module again, without its lock, and writes the new lockfile to `antelope-lock/`. It does so even when the version of the module does not change, which is how a dependency fix reaches a project. It then removes the locks that no environment uses. `--dry-run` changes no lock.

Then, unless `--dry-run` is set, the command checks the interface packages of the environment as `install` does. [Interface version check](#interface-version-check) describes the check and `--fix`.

```text
✔ antelope-lock/@antelopejs/api@1.5.0 changed
✔ antelope-lock/@antelopejs/mongodb@1.6.0 added
✔ Removed antelope-lock/@antelopejs/mongodb@1.5.2: no environment uses it
```

```bash
ajs project modules update [modules...] [options]
```

| Argument  | Description                                    |
| --------- | ---------------------------------------------- |
| `modules` | Modules to update (default: every npm module)  |

| Option                    | Description                                             |
| ------------------------- | ------------------------------------------------------- |
| `-p, --project <path>`    | Path of the project folder (default: current directory) |
| `-e, --env <environment>` | Environment of `antelope.config.ts` to update           |
| `--dry-run`               | Show the updates without applying them                  |
| `--fix`                   | Apply the interface package bumps the check finds       |

**Examples:**

```bash
# Update all npm modules
ajs project modules update

# Preview updates without applying
ajs project modules update --dry-run

# Update a specific module
ajs project modules update @antelopejs/api
```

### `ajs project modules install`

Find the interfaces that the modules of the project import but no module implements, and add a module from the interface repository that implements each of them. The command does not install npm dependencies, whatever its name suggests. It completes the module set of the project.

```bash
ajs project modules install [options]
```

| Option                    | Description                                                                   |
| ------------------------- | ----------------------------------------------------------------------------- |
| `-p, --project <path>`    | Path of the project folder (default: current directory)                       |
| `-e, --env <environment>` | Environment of `antelope.config.ts` to complete                               |
| `-g, --git <url>`         | Interface repository URL, overriding the `git` CLI setting (`ajs config get git`) |
| `-y, --yes`               | Add the first module listed when several implement an interface               |
| `--fix`                   | Apply the interface package bumps the check finds                             |

**Examples:**

```bash
ajs project modules install

# In CI: never prompt, take the first implementation when there is a choice
ajs project modules install --yes
```

::note
`install` looks in your modules for interface imports that no module in the project implements. It then looks up the modules that implement them in the interface repository and adds them. When a single module implements an interface, the command adds it without a question. When several modules implement it, the command asks which one to add. Without a terminal, it exits with code `2` and asks for `--yes` instead.
::

After it adds the modules, the command runs the [interface version check](#interface-version-check) on each analyzed environment. It prints its summary of the added modules first, without the next steps when the check fails, and the modules stay in `antelope.config.ts`.

### Interface version check

Modules share one copy of each interface package. `install` and `update` load the modules of the environment as `ajs project build` does and look, for each interface package, for the highest installed copy that every module's range accepts. When the copy a launch would share is older than that version, the command exits with code `1` and names the change each module needs:

```text
✖ Interface packages need a newer copy
  mongodb installs @antelopejs/interface-database 0.3.0; resolving its dependencies again gives 0.3.1, required by app@0.0.1
  → Run ajs project modules install --fix to apply the changes
  → Or run ajs project modules update mongodb
```

- A local module of the project that holds an older copy gets a raised floor in its `package.json`, such as `@antelopejs/interface-data-api: ^0.1.8 → ^0.1.9`. The other ranges keep their shape: `>=0.3.0 <0.4.0` becomes `>=0.3.1 <0.4.0`.
- An npm module whose older copy is the shared one resolves its dependencies again, as `ajs project modules update <module>` does, which writes a new lock to `antelope-lock/`.
- Other npm modules keep their own copy. A launch redirects them to the shared one.

`--fix` applies these changes, installs the dependencies of each local module it edits, and checks again. When only a local module of the project holds an older copy and the launch would still work, the command prints the same lines as a warning and exits with code `0`: the runtime uses the shared copy while TypeScript compiled the module against its own. When no installed copy satisfies every range, the command prints the `Incompatible interface package resolution` error with each module, its range and the shared version.

For an interface that no module implements, the shared copy is the highest installed copy that every module's range accepts, whatever the order of the modules in `antelope.config.ts`.

## Module locks

An npm module installs its own dependencies in `.antelope/cache/<module>`, from the ranges in its `package.json`. Pinning the version of the module in `antelope.config.ts` does not pin those dependencies, so the same commit built on two different days can install two different sets of versions.

The first time the core installs an npm module, it records in the project the lockfile that the package manager of the module wrote:

```text
antelope-lock/
├── @antelopejs/api@1.5.0/pnpm-lock.yaml
└── @antelopejs/dms@0.11.1/package-lock.json
```

Commit `antelope-lock/` with `antelope.config.ts`. From then on, `build`, `dev`, and `modules add|install` install each module from its lock, with the frozen install of its package manager (`pnpm install --frozen-lockfile` or `npm ci`). The core installs a cached module again when another lockfile installed it. A locked range such as `^1.5.0` stays on its recorded version until `ajs project modules update`. Each version has its own lock, so environments that pin different versions of a module get one lock each, whichever `--env` you build.

In CI and image builds, pass `--frozen-modules` to `ajs project build`. The build then fails on an npm module without a lock, an optional module included, instead of resolving its dependencies on the day of the build. It writes nothing in `antelope-lock/`.

`ajs project start` and the embedded runtime only replay the locks. A module loaded while the project runs installs from its lock when it has one, and nothing at run time writes in `antelope-lock/`.

```bash
ajs project build -e production --frozen-modules
```

```text
✖ No module lock for @antelopejs/api@1.5.0
  --frozen-modules installs only from antelope-lock/@antelopejs/api@1.5.0, and the project has none.
  → Run ajs project build without --frozen-modules (or ajs project modules update @antelopejs/api) and commit the lock it writes
```

Git and local modules have no lock. They install from their own working tree and lockfile.

A dist-tag such as `latest` has no lock of its own. The registry resolves it to a version on every install, and each version it resolves to gets its own lock. `ajs project modules update` resolves every npm module it selects again, whether or not a newer version exists. It records the lockfiles that result and removes the locks that no environment uses. Review the diff of `antelope-lock/` as you would review a dependency bump.
