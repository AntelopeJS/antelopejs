## Key terms

This glossary defines the core terms of the AntelopeJS documentation. Each entry gives a short definition and, where one exists, links to the page with the details.

### Interface

A TypeScript contract that declares the functions, events, or registrations a module can implement (produce) or consume. A consumer imports the interface, not the module behind it, so modules communicate without depending on each other. At run time, the core decides which module provides each interface.

See [Interfaces](/docs/concepts/interfaces).

### Module

A self-contained unit of functionality, packaged as a standard npm package, whose lifecycle the core manages. A module provides or consumes interfaces and moves through the states loaded, constructed, and active under the control of the core.

See [Modules](/docs/concepts/modules).

### Proxy

The object that carries communication between modules through an interface. AntelopeJS has three proxy types: `InterfaceFunction` for async function calls, `EventProxy` for events, and `RegisteringProxy` for registrations.

See [Proxies](/docs/concepts/proxies).

### Binding

The association between an interface producer, the module that implements the interface, and a consumer, the module that uses it. The core resolves the bindings when it loads the modules, before any module constructs. A call through a bound interface waits until the provider attaches its implementation.

### Implementation

The code in a module that fulfills an interface contract. An implementation maps each proxy that the interface declares to a real function, event handler, or registration handler inside the module.

### Contract

Another word for interface. It appears most in contract tests, which check that an implementation fulfills the interface it claims to provide. A contract test runs the same assertions against every module that implements a given interface.

### Lifecycle

The sequence of callbacks a module goes through: `construct`, `start`, `stop`, then `destroy`. The module moves from the loaded state to constructed, then to active, and back. The core runs these transitions and keeps their order across all modules.

See [Architecture](/docs/get-started/architecture).

### Core

The AntelopeJS runtime that loads modules, runs their lifecycle, and routes interface calls. The core resolves the dependency graph between modules, manages bindings, and runs the machinery behind interface-based communication.

### Hot module reloading

Hot module reloading (HMR) reloads one module at run time during development, without restarting the whole application. HMR destroys the module, stopping it first, then loads, constructs, and starts the replacement. The other modules keep running and keep their state. With the `--watch` flag, `ajs project dev` reloads a module when its source files change.

See [Modules](/docs/concepts/modules).

### Standalone mode

The mode in which the `ajs` CLI owns the process. `ajs project dev` or `ajs project start` reads `antelope.config.ts`, loads the modules, and handles signals and logging.

See [Embedded runtime](/docs/concepts/embedded-runtime).

### Embedded mode

The mode in which an existing application owns the process and runs AntelopeJS as a guest. The application lists its modules in `createRuntime()`, starts and stops the runtime from its own lifecycle, and reaches interfaces through `runtime.use()`.

See [Embedded runtime](/docs/concepts/embedded-runtime).
