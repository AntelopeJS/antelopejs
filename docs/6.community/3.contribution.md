## Contributing guide

Choose a focused change, verify it, and explain it in a pull request. Follow the [contribution policy](https://github.com/AntelopeJS/antelopejs/blob/main/CONTRIBUTING.md) and the development commands of the target repository. Ecosystem packages can have different prerequisites.

## Ecosystem overview

The AntelopeJS organization hosts the framework, the interfaces and the modules that implement them.

| Organization                                | Purpose                             |
| ------------------------------------------- | ----------------------------------- |
| [AntelopeJS](https://github.com/AntelopeJS) | Core framework and official modules |

## Ways to contribute

### Community support

- Answer questions in #support on the AntelopeJS [Discord server](https://discord.gg/g4pFt6eXqu)
- Help triage issues by reproducing reported bugs
- Share your solutions to common problems
- Give feedback on new features and proposals

### Reporting issues

Before you create an issue:

1. For a bug, follow the [bug reporting guide](/docs/community/how-to-report-bugs).
2. For a feature request, search the existing issues first.
3. Submit an idea for one module to the repository of that module.
4. Post a broader idea in #support on the AntelopeJS [Discord server](https://discord.gg/g4pFt6eXqu).

### Documentation improvements

Users depend on the documentation to succeed. You can:

- Fix typos or clarify existing content
- Add missing examples or code samples
- Improve the organization or navigation
- Translate documentation to other languages

## Pull request process

### Before starting

1. For a bug fix, check whether an issue already exists.
2. For a feature, open an issue first so that maintainers can agree on the goal.
3. For typo fixes, combine several corrections in one pull request.

### Development workflow

1. Fork the repository to your GitHub account.
2. Clone your fork to your machine.
3. Create a branch with a descriptive name.
4. Make your changes, following the code standards.
5. Write tests for new features and bug fixes.
6. Run the tests locally and check that they pass.
7. Submit your pull request.

### Commit guidelines

Commit messages follow the [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) standard:

```text
<type>(<scope>): <description>

[optional body]

[optional footer]
```

The common types are:

- `feat`: a new feature for the user, not a new feature for a build script
- `fix`: a bug fix for the user, not a fix to a build script
- `docs`: changes to the documentation
- `style`: formatting, such as missing semicolons, with no production code change
- `refactor`: a change to production code with no behavior change, such as renaming a variable
- `test`: adding missing tests or refactoring tests, with no production code change
- `chore`: repository maintenance with no user-facing behavior change
- `ci`: changes to continuous integration, such as GitHub Actions workflows
- `build`: changes to the build system or to external dependencies, such as npm, yarn, or build scripts

Examples:

```text
feat(api): add support for custom headers
fix(auth): correct token validation logic
docs(readme): update installation instructions
```

### Pull request guidelines

- Write a clear, descriptive title that follows the commit conventions
- Reference related issues in the description, for example "Fixes #123"
- Keep each pull request focused on one task or feature
- Answer reviewer feedback promptly

## Decision making process

Maintainers review the problem, the implementation, the compatibility and the verification evidence. Include the commands you ran and their results in the pull request, and call out any breaking changes. The contribution policy does not set a fixed number of approvals. Follow the review requirements of the target repository.

Repositories normally squash pull requests, so the pull request title becomes the commit title on the default branch.

## Creating generic interfaces

If you built something useful with AntelopeJS, consider turning it into a generic interface that others can implement.

### Why create generic interfaces?

- **More implementations.** A generic interface lets several modules implement the same contract.
- **Choice.** Users can switch between implementations to fit their needs.
- **Shared work.** Different developers can each own one implementation.
- **Common patterns.** Projects across the ecosystem use the same contracts.

### From feature to interface

1. Find functionality that several implementations could provide.
2. Describe its core behavior as an interface definition.
3. Document what the interface requires.
4. Create a reference implementation as a module.

### Interface best practices

- Give each interface a single responsibility
- Leave room to extend the interface later
- Provide detailed type definitions
- Include usage examples in the documentation
- Reference related interfaces where they apply

For details, read [Creating a module](/docs/module-development/creating-a-module) and [Exporting interfaces](/docs/module-development/exporting-interfaces).

## Proposing framework changes

For significant framework changes:

1. Implement your idea as a module first, when you can.
2. Open a **Feature request** issue with code examples and your reasons.
3. Maintainers may mark the proposal as an RFC (request for comments).

Agree on the scope and the compatibility with maintainers before you treat a proposal as an accepted implementation plan. Use the labels and tracking conventions of the target repository.
