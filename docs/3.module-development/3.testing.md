## Running Tests

Test the behavior consumers depend on through the public interface. The CLI loads the modules listed in your test configuration and runs Mocha tests. The example below tests the in-memory user directory from [Exporting Interfaces](/docs/module-development/exporting-interfaces); it needs no database.

```bash
ajs module test
```

To run a specific test file instead of the entire suite:

```bash
ajs module test -f test/user-service.test.js
```

The runner initializes the configured modules, runs the selected tests, and tears down the modules afterward. It does not automatically compile your module or test files. Configure the module's build command below; the first test uses JavaScript so it needs no TypeScript test loader.

## Test Configuration

Point your module to a test configuration file by adding the `test` field in the `antelopeJs` section of `package.json`.

```json [package.json]
{
  "antelopeJs": {
    "test": "antelope.test.ts"
  }
}
```

List the module under test explicitly, as well as any providers it needs. Pointing `antelopeJs.test` at this file does not add the module to the runtime by itself.

```typescript [antelope.test.ts]
import { defineConfig } from "@antelopejs/interface-core/config";

export default defineConfig({
  name: "my-module-test",
  modules: {
    "my-module": {
      source: {
        type: "local",
        path: "./",
        installCommand: "pnpm exec tsc",
      },
    },
  },
  test: {
    folder: "test",
  },
});
```

| Field          | Description                                                         |
| -------------- | ------------------------------------------------------------------- |
| `modules`      | All modules to load, including the module under test                |
| `test.folder`  | Directory containing test files (defaults to `test`)                |
| `test.setup`   | Async function that runs before tests — can return config overrides |
| `test.cleanup` | Async function that runs after all tests complete                   |

`setup` runs **before modules load**. Use it to start disposable services and return the connection settings modules need. It cannot call an interface that those modules have not implemented yet. Seed data through a Mocha `before` hook after startup instead. Failed assertions still lead to module teardown and `cleanup`. A teardown error can prevent the cleanup hook from running; use disposable services with an independent shutdown mechanism rather than relying on that hook as your only safeguard.

The order is: **setup → load → construct → start → tests → destroy → cleanup**. Keep resources created by `setup` reachable by `cleanup`, and make cleanup tolerate partial setup.

## Test File Conventions

Test discovery recursively includes `.test.ts`, `.spec.ts`, `.test.js`, and `.spec.js` files. Discovery is not compilation: for TypeScript tests, arrange a compatible loader or compile them first and point `test.folder` at the compiled output. Avoid scanning both source and compiled copies.

```
my-module/
├── test/
│   ├── user-service.test.js
│   ├── auth.test.js
│   └── helpers/
│       └── fixtures.ts
└── antelope.test.ts
```

Helper files and fixtures that do not match the test pattern are not executed as tests. You can import them from your test files to share setup logic or test data.

## Stub Mode

After module startup, the runner enables stub mode. Calls without an attached implementation then fail instead of waiting indefinitely for one to attach.

- `InterfaceFunction` calls reject with "Interface function called without implementation in test environment" unless a loaded module provides the implementation
- `RegisteringProxy.register()` throws the same error if no module handles the registration

This behavior forces you to explicitly load all required modules in your test configuration. Tests become isolated and predictable because every dependency must be declared upfront.

::warning
If a test fails with "Interface function called without implementation in test environment", check that the module providing that interface is listed in your test configuration's `modules` section.
::

## Writing Tests

Create this CommonJS test in the module directory. It calls the compiled public interface from the user-directory example, using Node's built-in assertions. No assertion-library dependency is required.

```javascript [test/user-service.test.js]
const assert = require("node:assert/strict");
const { GetUser, CreateUser, DeleteUser } = require("../dist/interface");

describe("User Service", () => {
  it("creates, retrieves and deletes a user", async () => {
    const user = await CreateUser("Alice", "alice@example.com");
    const retrieved = await GetUser(user.id);
    assert.equal(retrieved.name, "Alice");
    assert.equal(retrieved.email, "alice@example.com");

    await DeleteUser(user.id);
    await assert.rejects(GetUser(user.id), /User not found/);
  });
});
```

Run `ajs module test` from the module root. Expect one passing test. The read assertions catch a provider returning the wrong data; the rejection after deletion catches a no-op delete. Both exercise the public contract rather than the private map that stores users.

::note
The test runner uses Mocha under the hood. You can use any assertion library compatible with Mocha, including Chai, Node's built-in `assert`, or any other library that throws on failure.
::

## Interface Tests

Standalone interface packages can include their own test files in a `tests/` directory. These tests define the expected behavior of the contract — any module that implements the interface must pass them.

```
@antelopejs/interface-email/
├── src/
│   ├── index.ts              # Interface contract
│   └── tests/
│       └── send.test.ts      # Contract tests
└── dist/
    └── tests/
        └── send.test.js      # Compiled tests
```

When you run `ajs module test` on an implementing module, the test runner automatically discovers and runs these interface tests. The runner reads the `implements` array from the module's `package.json`, locates each interface package, and looks for compiled test files in `dist/tests/`. The runner then combines the interface tests with the module's own local tests and executes them all together.

```
Test execution order:
1. Local tests from the module's test/ directory
2. Interface tests from each package listed in implements
```

The interface author writes the suite once and each provider can run it against its implementation. Passing establishes compatibility for the behaviors the suite checks, not every possible use of the contract. Missing or unresolvable interface suites are skipped; inspect the reported tests rather than assuming a passing empty suite validates the provider.

::note
Passing `-f` replaces automatic discovery, including interface suites. Run `ajs module test` without `-f` before publishing a provider.
::

::tip
When creating a standalone interface package, include tests that verify the contract behavior. These tests act as a compliance suite — any module claiming to implement the interface must pass them.
::

## Implementation-Specific Tests

A module can include its own tests alongside the interface tests. Local tests in the module's `test/` directory cover implementation-specific behavior that the interface contract does not define.

```
my-email-module/
├── test/
│   ├── retry-logic.test.ts     # Implementation-specific
│   └── rate-limiting.test.ts   # Implementation-specific
└── package.json                # implements: ["@antelopejs/interface-email"]
```

The test runner collects both sets of test files and runs them in a single Mocha session. Interface tests verify that the contract is fulfilled, and local tests verify that implementation details work correctly.

## Testing with Dependencies

When your module depends on interfaces from other modules, declare those modules in the test configuration. The test runner loads them and resolves all interface bindings before running tests.

The following configuration is a sketch for an application with local auth and database modules, not a replacement for the self-contained example above. Keep the module under test in `modules`, supply each provider's actual configuration, and build local providers before loading them.

```typescript [antelope.test.ts]
import { defineConfig } from "@antelopejs/interface-core/config";

export default defineConfig({
  name: "my-module-test",
  modules: {
    "my-module": {
      source: { type: "local", path: "./", installCommand: "pnpm exec tsc" },
    },
    "auth-module": {
      source: { type: "local", path: "../auth-module" },
      config: { secretKey: "test-secret" },
    },
    "db-module": {
      source: { type: "local", path: "../db-module" },
      config: { connectionString: "mongodb://localhost/test" },
    },
  },
  test: {
    folder: "test",
    cleanup: async () => {
      // Drop test database after tests
    },
  },
});
```

Each module in the `modules` section receives its own `config` object. Use test-specific values — test database URLs, mock API keys, or reduced timeouts — to keep tests fast and isolated from production data.

::tip
Keep test configurations minimal. Only load the modules your tests actually depend on. Fewer modules mean faster test startup and clearer failure messages when something breaks.
::
