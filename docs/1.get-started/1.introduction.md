## Hexagonal architecture. Beyond your own code.

AntelopeJS is a TypeScript framework and CLI for Node.js applications. It puts your business modules, your local integrations, and the ecosystem modules you install into the same ports-and-adapters model. Consumers depend on explicit contracts, providers implement them, and the application selects the implementations.

If you already practice hexagonal architecture, AntelopeJS does not ask you to learn another folder structure. It supplies interface binding, a module lifecycle, and application assembly. Those mechanisms let the same boundaries hold across modules that different teams maintain and release.

## Keep the boundary when you add a dependency

An integration should not force business modules to import the provider that implements it. In AntelopeJS, a consumer calls an interface package. A provider registers an implementation of that interface, and the runtime connects the calls.

For example, a consumer can depend on the shared database contract instead of a MongoDB module. The implementation can come from your own code or from the ecosystem, and both take part in the same module model. A consumer can also call a MongoDB-specific interface, but that choice gives up portability on purpose.

## What AntelopeJS provides

::card-group
::card{icon="i-ph-brackets-curly" title="Explicit contracts"}
Describe the capabilities consumers need through typed interface APIs. Keep the provider choice outside the consuming module.
::

::card{icon="i-ph-puzzle-piece" title="One ecosystem model"}
Compose local modules and published packages through the same application configuration and lifecycle. You do not need a separate integration model for each module source.
::

::card{icon="i-ph-arrows-split" title="Application-owned choices"}
Select an implementation in application configuration. A compatible replacement keeps the consumer's import and calls, while its provider-specific setup changes.
::

::card{icon="i-ph-code" title="Shared runtime mechanisms"}
Use interface binding and the module lifecycle instead of building that infrastructure again. You stay responsible for your contracts, business behavior, and integration tests.
::

::card{icon="i-ph-rocket-launch" title="Development hot reload"}
Reload changed local modules during development. Hot reload shortens the edit-and-run loop. It is separate from changing a production provider.
::
::

## What stays your responsibility

A replacement must support the contract version, capabilities, and behavior your consumers require. Matching types alone do not make two providers compatible. Configuration, credentials, data migrations, and operational requirements still need your attention.

AntelopeJS gives you the mechanisms for explicit boundaries. It does not stop a module from importing a provider directly. Your design still decides which dependencies belong in business code, and consumers stay coupled to their contracts.

::note
Hot module reloading is a development feature. It does not migrate a running production application from one provider to another.
::
