## Prerequisites

The Data API builds on both the API and database systems. Install all three interface packages in your module.

:::code-group

```bash [npm]
npm install @antelopejs/interface-data-api @antelopejs/interface-api @antelopejs/interface-database-decorators
```

```bash [yarn]
yarn add @antelopejs/interface-data-api @antelopejs/interface-api @antelopejs/interface-database-decorators
```

```bash [pnpm]
pnpm add @antelopejs/interface-data-api @antelopejs/interface-api @antelopejs/interface-database-decorators
```

:::

Import from these packages as needed:

- `@antelopejs/interface-data-api` -- `DataController`, `RegisterDataController`, `DefaultRoutes`
- `@antelopejs/interface-api` -- `Controller`
- `@antelopejs/interface-database-decorators` -- Table definitions and models

Before using the Data API, you need a registered table. Refer to the [Database guide](/docs/guides/database) for table setup.

## Choose generated routes deliberately

Use generated CRUD routes for tables whose read/write rules match the exposed operations. Import the controller file from the module entry point, register its schema, and configure API and database providers. The interface package alone does not start either service.

For private or tenant-owned records, define authorization before exposing `DefaultRoutes.All`. Authentication verifies a token; it does not scope records to the caller. Start with only the routes you need, and use custom handlers when ownership rules require server-side filtering or checks.

## Creating a Data Controller

The `DataController` function generates a controller class with CRUD endpoints mapped to a database table. It accepts three arguments: the table class, a route definition object, and a base controller. The `@RegisterDataController()` decorator registers the generated controller with the framework.

```typescript fragment [src/data-api/tasks.ts]
import {
  DataController,
  RegisterDataController,
  DefaultRoutes,
} from "@antelopejs/interface-data-api";
import { Controller } from "@antelopejs/interface-api";
import { BasicDataModel, Model } from "@antelopejs/interface-database-decorators";
import {
  Access, AccessMode, Listable, Mandatory, ModelReference,
} from "@antelopejs/interface-data-api/metadata";
import { Task } from "../db/tables/task";

class TaskModel extends BasicDataModel(Task) {}

@RegisterDataController()
class TaskDataController extends DataController(
  Task,
  {
    get: DefaultRoutes.Get,
    list: DefaultRoutes.List,
    new: DefaultRoutes.New,
    edit: DefaultRoutes.Edit,
    delete: DefaultRoutes.Delete,
  },
  Controller("/api/tasks"),
) {
  @ModelReference()
  @Model(TaskModel)
  declare model: TaskModel;

  @Listable()
  @Access(AccessMode.ReadOnly)
  declare _id: string;

  @Listable()
  @Mandatory("new")
  @Access(AccessMode.ReadWrite)
  declare userId: string;

  @Listable()
  @Mandatory("new")
  @Access(AccessMode.ReadWrite)
  declare title: string;

  @Listable()
  @Mandatory("new")
  @Access(AccessMode.ReadWrite)
  declare description: string;

  @Listable()
  @Mandatory("new")
  @Access(AccessMode.ReadWrite)
  declare completed: boolean;
}
```

Use the Task table in [Combining with the Database Guide](#combining-with-the-database-guide). The model and field declarations are required, not decoration around the routes:

| Declaration | Responsibility |
| --- | --- |
| `@ModelReference()` + `@Model(TaskModel)` | Connect generated handlers to a model instance. Without them, requests fail with `Missing model key`. |
| `@Access` | Select fields that may be read or written. A table column alone does not expose an API field. |
| `@Listable` | Select fields for list responses; read access is also required. |
| `@Mandatory("new")` | Require a field when creating, without requiring it on partial edits. |

This controller creates five endpoints:

| Route                              | Method                 | Description             |
| ---------------------------------- | ---------------------- | ----------------------- |
| `GET /api/tasks/get?id=<id>`       | `DefaultRoutes.Get`    | Retrieve a single task  |
| `GET /api/tasks/list`              | `DefaultRoutes.List`   | List all tasks          |
| `POST /api/tasks/new`              | `DefaultRoutes.New`    | Create a new task       |
| `PUT /api/tasks/edit?id=<id>`      | `DefaultRoutes.Edit`   | Update an existing task |
| `DELETE /api/tasks/delete?id=<id>` | `DefaultRoutes.Delete` | Delete a task           |

The final path segment matches the key you used in the route definition (`get`, `list`, `new`, `edit`, `delete`). Identifiers for single-record routes are passed as the `id` query parameter, not as a path segment.

::note
`DataController` is a function that returns a class, not a decorator. Use `extends DataController(...)` to create your data controller.
::

## Using DefaultRoutes.All

When you need all five CRUD routes, `DefaultRoutes.All` provides a shorthand that includes `Get`, `List`, `New`, `Edit`, and `Delete` in a single declaration.

Replace only the second argument of `DataController` with `DefaultRoutes.All`. Keep the model property and field decorators from the complete controller above.

The shorthand produces the exact same set of endpoints as the explicit route definition. Use the explicit form when you need to include only specific routes or apply different options to each route.

## Selective Routes

You can include only the routes your API needs by listing a subset in the route definition. Omitted routes are not generated.

For a read-only controller, use this route map as the second argument and change the base path to `/api/public/tasks` if needed:

```typescript fragment
{
  get: DefaultRoutes.Get,
  list: DefaultRoutes.List,
}
```

This controller exposes only `GET` endpoints. No create, update, or delete operations are available, making it suitable for public or read-only APIs.

## Adding Authentication

`@Authentication` from `@antelopejs/interface-auth` works as a class decorator. Applied to the Data API controller, it registers an auth check as a computed property on the controller, which the framework evaluates for every incoming request before any handler runs.

Install `@antelopejs/interface-auth`, configure its provider, import `Authentication` from that package, and add `@Authentication()` beneath `@RegisterDataController()` on the complete controller above. Keep the model and field declarations. The [task tutorial](/docs/guides/full-stack-tutorial#create-the-task-data-api) shows the full authenticated class.

Every route now requires a valid authentication token. Requests without authentication are rejected before reaching the route handler.

Every authenticated user can still reach the same default CRUD operations. A `userId` column or relation does not turn this into owner-only access. Never trust a client-supplied owner ID as an authorization decision.

## Mixed Access Patterns

Class-level `@Authentication()` is all-or-nothing. When you need a mix of public read endpoints and protected write endpoints on the same table, split the routes across two controllers mounted at the same base path — one protected, one public.

For articles, both controllers use the Article table and its model, but expose disjoint route maps:

| Controller | Route map entries | Authentication |
| --- | --- | --- |
| Public reads at `/api/articles` | `get: DefaultRoutes.Get`, `list: DefaultRoutes.List` | None |
| Protected writes at `/api/articles` | `new: DefaultRoutes.New`, `edit: DefaultRoutes.Edit`, `delete: DefaultRoutes.Delete` | Class-level `@Authentication()` |

Each controller still needs its model reference and field access metadata. Anyone can read the exposed article fields; any authenticated user can perform the generated writes. Add a role or ownership policy if that is too permissive.

## Custom Route Options

The `DefaultRoutes.WithOptions` function accepts an optional third argument for the endpoint path. The third argument replaces the final path segment of a specific route.

```typescript fragment
DefaultRoutes.WithOptions(DefaultRoutes.Get, {}, "by-id");
```

With this override the Get route becomes `GET /api/tasks/by-id?id=<id>` instead of the default `GET /api/tasks/get?id=<id>`. The options object forwards query-parameter defaults to the route handler (for example `{ noPluck: true }` or `{ noForeign: true }`); it is not a place to plug in authentication. Use custom endpoints when the default URL segment does not match your API design or when you need to avoid conflicts with other controllers.

## Combining with the Database Guide

The Data API works directly with tables defined using the database decorators. Here is a complete example that defines a table and exposes it as a CRUD API.

```typescript fragment [src/db/tables/task.ts]
import {
  Table,
  RegisterTable,
  Field,
  Index,
  Relation,
} from "@antelopejs/interface-database-decorators";
import { User } from "./user";

@RegisterTable("tasks", "main")
class Task extends Table {
  @Index()
  @Field("string")
  @Relation({ to: () => User })
  declare userId: string;

  @Field("string")
  declare title: string;

  @Field("string")
  declare description: string;

  @Field("boolean")
  declare completed: boolean;
}

export { Task };
```

Use this table with the complete controller above, import both from your module entry point, and await `RegisterSchema("main")` during `construct()`. The referenced User table comes from the [Database guide](/docs/guides/database#defining-tables).

Table metadata supplies storage types; controller metadata supplies API access. For filtering, declare the appropriate Data API filter metadata rather than assuming a database index exposes a query parameter automatically. The [interface reference](https://interfaces.antelopejs.com/docs/data-api) covers access rules, validators, filters and relations.

## Verify the generated API

Send writable fields directly in the JSON body, not inside a `data` property. For the task table above, include `userId`, `title`, `description` and `completed` when creating a record. Edits take the record ID from `?id=...`.

List requests return an envelope with `results`, `total`, `offset` and `limit`, not a bare array. Check the response envelope and both an existing and missing ID. If you add authentication, also test missing and invalid tokens; those checks do not replace authorization tests between two users.
