Start with the first error, not the cleanup messages after it. Capture the module ID, lifecycle phase, `ajs --version`, Node.js version and command. Use `--verbose` for the underlying exception; redact credentials before sharing logs.

| Symptom | First check |
| --- | --- |
| `dist/index.js` is missing | Build the module and verify `package.json.main`; watch mode needs a configured build command. |
| Required interface has no provider | Add a provider to the project, not just the interface to `dependencies`. |
| Incompatible interface package resolution | Compare the shared interface version in the error with each consumer's declared range; reinstall compatible dependencies. |
| Startup waits without completing | Check construction cycles and interface calls inside `provide()`. |
| A route returns 404 | Import its controller file from the module entry point and rebuild. |
| A reload fails | Read the original build/construct/start error, fix it, then save again. |
| Embedded host calls hang | Use `runtime.use()` after startup instead of a plain interface import. |

### Interface not implemented

::note
This error occurs in test mode when using stubs. The test runner uses stub mode by default, which rejects calls to interfaces that have no registered implementation.
::

Your test calls an interface function, but no module provides that interface in the test environment. Stub mode raises this error immediately rather than hanging on an unresolved proxy.

::tip
Load a real or test-provider module in the test configuration's `modules` map. Have that provider attach its implementation during `construct()`. The runner's `setup()` runs before module loading, so it is not a place to call those interfaces.
::

### Incompatible interface package resolution

The runtime found providers, but the interface package it selected does not satisfy every consumer's declared range. The error names the consumer, its range, and the shared copy's version and path. This differs from a missing provider: adding another provider alone does not fix the version disagreement.

For example, `^0.0.14` excludes `0.0.15`. Check the newer contract's changes, update the affected consumer to a compatible release or range, and reinstall its dependencies. Providers must implement every required function before widening their supported range; do not silence the error by claiming compatibility you have not tested.

### Module failed to construct

::note
The `construct()` function threw an error during the module's initialization phase. Common causes include missing configuration values, unavailable external dependencies, or invalid setup logic.
::

Failure of a required module fails launch and triggers cleanup of partially constructed modules. Other construction work can already be in flight. The error identifies the failing module and original exception; cleanup errors can appear alongside it.

::tip
Check your module's `construct()` function and verify the configuration passed via `antelope.config.ts`. Make sure all required configuration keys are present and that external services (databases, APIs) are reachable before attempting to connect.
::

### Module failed to start

::note
The `start()` function threw an error. Since `start()` runs after all modules have been constructed and bindings are resolved, this typically indicates a runtime issue rather than a configuration problem.
::

The runtime awaits start callbacks, including other starts already in flight, and cleans up a failed required launch. The failed module never becomes active, so its `destroy()` must work without a preceding `stop()`.

::tip
Ensure external services your module depends on are available at start time. If a service may be temporarily unavailable, handle the error internally with try/catch and implement a retry strategy or graceful degradation.
::

### Unresolved interface dependencies

::note
The core validates the interface dependency graph before constructing modules. If a required interface has no provider in the current configuration, the boot fails with this error.
::

This error means a module declares that it consumes an interface, but no loaded module implements that interface. The core detects this before any `construct()` call, so the application never partially starts.

::tip
Verify that all required modules are listed in `antelope.config.ts` and that each one implements the expected interfaces. Check for typos in interface package names and ensure the implementing module's `package.json` includes the correct `implements` entry.
::
